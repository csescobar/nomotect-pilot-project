# RFC Process

## When an RFC is required

Use an RFC for changes that introduce a major capability, alter public contracts, cross module boundaries, change security posture, add a foundational dependency or modify the Engineering Constitution.

## Lifecycle

1. **Draft:** describe problem, constraints, proposal, alternatives and risks.
2. **Discussion:** collect technical, security, product and operational feedback.
3. **Decision:** accept, reject or request revision.
4. **ADR:** record the accepted decision and consequences.
5. **Implementation:** deliver through focused issues and pull requests.
6. **Validation:** compare implementation evidence with the accepted RFC.

## Required sections

- Summary
- Motivation
- Scope and non-goals
- Proposed design
- Public contracts
- Security and privacy impact
- Accessibility and i18n impact
- Operations and migration
- Alternatives
- Rollback or exit strategy
- Open questions

RFC discussion must not be hidden exclusively in agent memory or private tooling.
